# 日志与观测 · 规格说明 v0.2

> 状态：设计定稿，尚未实现。日期：2026-11-15（v0.2 吸收首轮审阅意见，修订记录见 §15）。
> 适用范围：`shared/agentloop`、`memory-system/`、`trpg/` 三个子项目共用；实现位于 `shared/observability`。
> 目标不是"出了问题能查"，而是**为后续优化提供可比较、可回放的数据**：每一次子 agent 运行都能离线重跑、每一个阈值都能用历史数据校准。

---

## 1. 目标

1. **可追溯**：任何一条发出的消息、写入的记忆、被打回的候选，都能沿 ID 链回溯到触发它的事件、经过的每一轮模型调用、每一道核查的裁决。
2. **可度量**：延迟、token、成本、缓存命中、核查拒绝率、召回命中、预算消耗，按任务类型、提示词版本、模型分组统计。
3. **可回放**：每次子 agent 任务保存"输入包"，可用新提示词或新模型离线重跑并对比结果，形成回归集。
4. **低开销、不阻塞**：日志写入异步、批量；观测故障绝不影响聊天与记忆写入。
5. **隐私可控**：聊天原文、账号 ID 与完整提示词只在本机、不外发、可按保留期清理。**不做脱敏**（§9）：这是后台运维数据，必须能看出是哪个账号的互动，回放也必须用原文才能和线上结果可比。

### 非目标
- 不接入外部 APM / 云监控（预留 OTLP 导出接口，v0.1 不实现）。
- 不做实时告警平台；只做阈值触发的私聊提醒与日报。

## 2. 三类数据

| 类 | 内容 | 存储 | 保留 |
|---|---|---|---|
| **事件日志（logs）** | 结构化 JSONL，一行一事件 | `logs/<component>/<YYYY-MM-DD>.jsonl`，按日轮转 | `log_keep_days`（默认 30） |
| **指标（metrics）** | 预聚合计数器 / 直方图，按分钟桶 | `obs.db`（SQLite）`metrics` 表 | `metrics_keep_days`（默认 180） |
| **回放包（replays）** | 子 agent 任务的完整输入、各轮输出、裁决 | `replays/<task>/<run_id>.json.zst` | `replay_keep_days`（默认 14）；被标记为回归用例的永久保留 |
| **基线（baselines）** | 某一时期的分组指标 + 抽样回放包的冻结快照 | `baselines/<名称>/` | 永久，搭档手动删除 |

另有 **审计表** `obs.db.audit`：只记有副作用的动作（写记忆、发消息、撤回、改配置、导入、迁移），永久保留，与事件日志互为索引。

**磁盘上限** `obs_max_disk_mb`（默认 2048）：超出时按顺序清理——抽样保存的回放包 → `debug` 日志 → 最旧的 `info` 日志 → 最旧的指标桶；**永不**删除审计表、回归集、基线。

**写入者**：只有 AstrBot 插件进程写 `obs.db` 与 `logs/`。海豹 JS 扩展（`trpg.bridge`）的日志通过桥接接口发给插件落盘；命令行重跑工具只读 `obs.db` 与回放包，自己的输出写 `replays/reruns/<时间戳>/`。

**时区**：`ts` 带时区存储；分钟桶、日报的"昨日"、保留期的"天"一律按 `Asia/Shanghai` 切分（与记忆规格 §16 一致）。

## 3. 关联 ID 链

```
turn_id        一次对大肥鱼的触发（一条入站消息或一次定时任务）
 └─ run_id     一次子 agent 任务（抽取 / 反思 / 摘要 / .ask / .sum / npc_speak / scene_interact …）
     └─ round  任务内第几轮（生成 1 → 核查 1 → 修正 2 …）
         └─ call_id   一次 Provider 调用
 └─ job_id     异步工作者任务（可无 turn_id，如定时折叠）
 └─ msg_id     实际发出的消息（可多条）
 └─ mem_id     写入 / 修改的记忆文件 name 或事件 ULID
```
- `turn_id`、`run_id`、`job_id`、`call_id` 均为 ULID。
- 所有日志行必带 `turn_id` 或 `job_id` 之一；子 agent 内的行必带 `run_id` 与 `round`。
- 发出的每条消息在审计表记录 `msg_id ↔ run_id`，TRPG 的 `.npc undo` 与记忆的 `write_event` 都靠它反查。

## 4. 日志行格式

```json
{"ts":"2026-11-15T21:03:12.481+08:00","lvl":"info","comp":"memory.extract","evt":"candidate_rejected",
 "turn_id":"01JC…","run_id":"01JC…","round":1,"scope":"real/admin","realm":"real",
 "task":"extract","gate":"source_precedence","reason":"inferred_vs_user_stated",
 "cand":"admin-dinner-status","dur_ms":0,"prompt_ver":"extract@3","cfg_hash":"a1b2c3"}
```

### 4.1 公共字段
| 字段 | 含义 |
|---|---|
| `ts` | 带时区的 ISO 8601，毫秒 |
| `lvl` | `debug` / `info` / `warn` / `error` |
| `comp` | 组件路径：`agentloop`、`memory.capture`、`memory.extract`、`memory.reflect`、`memory.summarize`、`memory.recall`、`memory.inject`、`memory.index`、`memory.watcher`、`trpg.router`、`trpg.stage`、`trpg.scribe`、`trpg.bridge`、`obs` |
| `evt` | 事件名（§5 枚举） |
| `turn_id` / `run_id` / `job_id` / `round` / `call_id` | 关联链 |
| `scope` / `realm` | 作用域（含真实群号 / QQ 号，§9） |
| `actor` | 触发者账号：`platform:id`（如 `qq:123456`）；事件日志与回放都保留原值 |
| `task` | 任务类型（§5.2） |
| `dur_ms` | 本事件覆盖的耗时 |
| `prompt_ver` | 提示词版本 `名称@标签+内容哈希`（§7） |
| `cfg_hash` | 本次运行生效配置的哈希（§7） |
| `astrbot_ver` / `plugin_ver` | 运行环境版本，`run_start` 与配置快照必带 |
| `payload_ref` | 指向回放包或大对象的引用（不内联大文本） |

### 4.2 Provider 调用行（`evt: provider_call`）
`provider_id, model, role(gen/critic/plan/compose/extract/reflect/summarize/score/embed/judge), tokens_in, tokens_out, tokens_cached, cost_est, latency_ms, status(ok/timeout/error/json_invalid), retry_no, prompt_sha(前缀哈希，用于缓存命中分析)`。

- `tokens_cached` **以 Provider 返回字段为准**（DeepSeek：`prompt_cache_hit_tokens`）；Provider 不返回时记 `null`，不记 0，指标聚合时跳过 null，避免换模型后缓存命中率被误读为 0。
- `role=judge` 专指观测系统自身发起的评估调用（§6.4），`task` 以 `obs_` 开头。

### 4.3 级别约定
- `debug`：每轮提示词与输出的引用、检索候选列表。默认不落盘，`debug_payloads=true` 时写入回放包。
- `info`：流程里程碑、裁决结果、注入组成、发送。
- `warn`：降级、超时、重试、预算告警、核查拒绝率异常。
- `error`：任务失败、数据不一致（悬空 evidence、索引与文件不符）、写入失败。

## 6. 指标

按分钟桶预聚合到 `obs.db.metrics(ts_min, comp, task, prompt_ver, model, name, kind(counter/hist), value/buckets)`。日报与 `/观测 报告` 由此生成。

### 6.1 质量
| 指标 | 定义 | 用途 |
|---|---|---|
| `gate_reject_rate{gate,task}` | 该门拒绝数 / 候选数 | 门太严（拒绝率 > 60%）或太松（< 5%）都要调 |
| `run_outcome{task,outcome}` | 各结局占比 | 兜底与存疑比例 |
| `rounds_per_run{task}` | 直方图 | 平均需要几轮修正，衡量提示词质量 |
| `fragment_hit_rate` | 被注入片段中命中的比例，**只按 `read` 与 `cited` 两级信号计算**；`similar` 单独展示为 `fragment_similar_rate` | 召回是否有用；调 `auto_topk`、权重 |
| `fragment_judge_agreement` | 抽样（§6.4）中 judge 判定与 `read`/`cited` 信号的一致率 | 校准命中判定本身 |
| `index_size{scope}` / `hot_demote_count` | 热索引大小与降级数 | 校准 `index_max_lines`、30 天规则 |
| `insight_lifecycle` | 写入 / 强化 / 反驳 / 休眠计数 | 反思质量趋势 |
| `summary_verified_rate` | 摘要通过准确性核查的比例 | 摘要提示词 |
| TRPG `leak_block_count{npc}` | 泄密核查拦截次数 | 哪张卡的秘密经常被逼问 |
| TRPG `review_change_rate` | 审后发中 KP 修改 / 放弃的比例 | NPC 质量的人工信号 |
| TRPG `undo_count` | 撤回次数 | 同上 |

### 6.2 性能与成本
| 指标 | 定义 |
|---|---|
| `latency_ms{comp,task}` | 直方图（p50 / p95） |
| `recall_latency_ms` / `recall_degraded_count` | 召回耗时与降级次数 |
| `inject_tokens{section}` | 核心 / 索引 / 片段各占 token |
| `cache_hit_ratio` | `tokens_cached / tokens_in`，按 `prompt_sha` 前缀分组 |
| `cost_est{task,model}` | 按配置单价估算的费用 |
| `budget_used{scope,kind}` | 预算消耗 |
| TRPG `e2e_latency_ms{mode,segment}` | 玩家消息到首条 NPC 消息（V10 的持续观测），**按段拆分**：`wake→main_agent`、`main_agent→subagent`、`subagent→first_sent`、`first_sent→last_sent` |
| `recall_latency_ms{segment}` | 召回按 `embed / search / rank` 拆分 |
| TRPG `dice_sync_lag_ms` | 海豹落库到同步 |

### 6.3 健康
`job_queue_depth`、`job_fail_count`、`provider_error_count{provider,status}`、`orphan_evidence_count`、`watcher_invalid_count`、`bridge_error_count`、`obs_dropped`、`obs_disk_mb`。

### 6.4 观测自身的模型调用
三级命中信号的校准（§6.1）与日报异常项的解释都需要调模型。规则：
- 统一 `role=judge`、`task=obs_*`；**在所有按任务分组的质量与成本指标中默认排除**，日报单独一行"观测自身成本"。
- 命中校准：每日从有片段注入的轮次中抽样 `obs_judge_sample`（默认 5%，上限 30 轮），用便宜模型判定"该片段是否被回复使用"，产出 `fragment_judge_agreement`。
- 日上限 `obs_daily_call_cap`（默认 50），超出即停，不影响被观测任务。

### 6.5 冷启动保护
任何按比率触发的提醒（§10）在分组样本数 < `alert_min_samples`（默认 30）时不触发；报告中该格显示样本数而不显示比率。

## 7. 版本与配置快照
- **提示词模板**全部放在仓库 `shared/prompts/<名称>.md`，头部声明可读标签 `# prompt: extract@3`。
- **`prompt_ver` 由代码生成**：`<名称>@<标签>+<内容 sha256 前 6 位>`，如 `extract@3+a1b2c3`。标签只是给人看的；真正区分版本的是内容哈希，忘记升标签也不会把两个版本的数据混在一起。
- **一致性检查**：启动时若发现同一标签对应多个历史哈希（内容改了、标签没升），在日志 `warn` 并私聊搭档提醒升标签；`strict_prompt_versions=true` 时拒绝加载。
- **配置快照**：每次运行记录生效配置的 `cfg_hash`，并把哈希 → 配置全文（含 `astrbot_ver`、`plugin_ver`、模型与 Provider 列表）存入 `obs.db.config_snapshots`（去重）。
- **模型**：`provider_call` 记录实际 `model` 与 `provider_id`。
- 日报与重跑报告按 `(prompt_ver, model, astrbot_ver)` 分组给出质量与成本，便于做 A/B 与升级前后对比。

### 7.1 基线
`/观测 基线 <名称>`：把最近 7 天（可指定范围）的分组指标、配置快照、以及按 §8.1 分层规则抽取的回放包复制到 `baselines/<名称>/`，永久保留。重跑工具 `--baseline <名称>` 用该基线的回放包作为输入、该基线的指标作为对照列。建议在每次大改提示词或升级 AstrBot 之前打一个基线。

## 8. 回放包与回归集

### 8.1 回放包内容与保存规则
**分层保存**（`debug_payloads=true` 时全部保存）：
| 运行结局 | 保存比例 |
|---|---|
| `failed` / `timeout` / `fallback` / `accepted_with_doubt` | 100% |
| TRPG 轮次随后被 `.npc undo` 撤回、或审后发中 KP 修改 / 放弃 | 100%（最有价值的负样本；撤回发生在保存之后时，补标 `kp_rejected=true` 并转为永久保留候选） |
| `accepted` | `replay_sample_rate`（默认 10%） |

```json
{"run_id":"…","task":"reflect","actor":"qq:123456","scope":"real/admin",
 "prompt_ver":{"gen":"reflect@2+9f8e7d","critic":"reflect_critic@1+3c2b1a"},
 "env":{"astrbot_ver":"4.29.0","plugin_ver":"0.1.0","model":"deepseek-chat","cfg_hash":"a1b2c3"},
 "inputs":{"evidence":[{"ep":"01JC…","speaker":"qq:123456","text":"原文"}],"context_files":["lesson-ask-once"],"question":"…"},
 "rounds":[{"round":1,"role":"gen","prompt_sha":"…","output":"…","tokens":{"in":1820,"out":210,"cached":1500}},
           {"round":1,"role":"critic","gates":[{"gate":"llm_consistency","pass":false,"reason":"…"}]}],
 "final":{"outcome":"fallback","output":null},
 "expected":null}
```
输入包保存**原文与真实账号 ID**，不脱敏（§9）；因此重跑结果与线上可比。

### 8.2 离线重跑
`python -m shared.observability.replay --task reflect --since 7d --prompt reflect@3 --model deepseek-chat [--baseline <名称>]`：
- 对历史回放包（或指定基线的回放包）用新提示词 / 新模型重跑生成与核查；
- 输出对比表：各门通过率变化、结局变化、token 与延迟变化、逐例 diff；有 `expected` 的用例额外给出符合 / 不符合；
- 只读 `obs.db`，输出写 `replays/reruns/<时间戳>/`；不触发任何副作用（不写记忆、不发消息、不写指标表）。

### 8.3 回归集与期望结局
每个回归用例必须有 `expected` 字段：
```json
"expected":{"outcome":"fallback",
            "gates_must_fail":["llm_consistency"],
            "must_not_contain":["一直没吃"],
            "note":"晚饭事故：用户已陈述吃完，反思不得产出相反结论"}
```
- **线上标记**：`/观测 标记 <run_id> 回归` 时先展示该运行的输入与结局，再让搭档选择"当时的结局正确"（`expected` = 实际结局）或"当时错了，应该是 X"（搭档填 `outcome` 与可选的 `must_not_contain`）。确认后复制到 `replays/golden/`，永久保留。
- **手工构造**：规格要求的回归场景（"晚饭事故"、泄密对抗、行为自述等）以同一格式手工编写，`actor` 用虚构账号。
- CI 跑 `replay --golden`，所有用例的 `expected` 必须全部满足。

## 9. 隐私
**决定：不做脱敏。** 这是搭档本机的后台运维数据，必须能看出是哪个账号的互动，回放必须用原文才与线上可比。隐私靠边界而不是靠改写：
- 日志、指标、回放、基线只存本机 `data/plugin_data/obs/`，`.gitignore` 排除，不入任何仓库，不外发；只读 HTTP 导出（§10）只监听 `127.0.0.1`。
- `info` 级日志记 `actor`（真实账号）、ID、长度、哈希，**不内联聊天原文**——原文在回放包与 `events.db` 中，减少日志体积而非出于脱敏。
- 回放包默认 14 天过期自动删除；回归集与基线永久，`.gitignore` 同样排除。
- `/观测 清理` 可立即删除全部非回归、非基线回放包。
- 备份随记忆系统的备份任务一起加密打包（记忆规格 §13）。
- 预留 `redact_export=true` 选项：仅在**导出给他人**（如提 issue、分享回归用例）时对导出副本做账号哈希与号码替换，本地数据不变。v0.1 不实现。

## 11. 实现要点
- `shared/observability` 提供：`log(evt, **fields)`、`span(comp, evt)` 上下文管理器（自动 `dur_ms`）、`stage(name)`（记录相对时间戳）、`metric.inc/observe`、`replay.save`、`baseline.freeze`、ID 生成与 contextvars 传递（`turn_id`/`run_id` 自动随协程传播）。
- **contextvars 传播**【待验证 V1】：AstrBot 内部在 `on_llm_request` → 工具调用 → 子 agent 之间若使用 `asyncio.create_task` 且未拷贝上下文，`turn_id` 会丢失。M0 实测；若丢失，退化方案是在 `event` 对象上显式挂 `turn_id`，`agentloop` 入口从 `event` 读取而不依赖 contextvars。
- 写入走内存队列 + 后台线程批量落盘；队列满则丢弃 `debug`、合并 `info`、保留 `warn/error` 并计数 `obs_dropped`。
- `agentloop` 内置埋点：所有子项目只要通过它调用 Provider，`provider_call`、`gate_result`、`run_*` 自动产生，不需要各自再写。
- 指标预聚合在进程内，每分钟刷到 `obs.db`；重启丢失最多 1 分钟。
- 对 AstrBot 自身日志（`astrbot.api.logger`）只做 `warn` 以上的镜像，避免重复。
